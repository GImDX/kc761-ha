### R5-005（P1）：写入时的底层自动重连未重新核验设备身份

- 位置：`coordinator.py` 行 452～482 的写路径；`protocol/client.py` 行 581～590；身份核验集中在 `coordinator.py` 行 232～255 的轮询新连接路径。
- 因果：控制门禁允许后，coordinator 直接调用 client；client 发现断开会连接并立即发送写请求，没有先经过 DEVICE_ID 核验。端点仍相同并不能证明重新连接的设备身份仍相同。
- 影响：身份绑定承诺没有覆盖每个承载写入的新连接；不声称本机当前已经写错设备。
- 防御修复方向：每个新连接必须先确认绑定身份，写入不能自行创建未经身份确认的新连接。只在上层写入前检查一次 `connected` 不足以消除检查与实际发送之间的变化。

### R5-006（P2）：同一状态字节的并发修改可能互相覆盖

- 位置：`coordinator.py` 行 418～446 的状态读改写、行 477～482 的发送和读回。
- 因果：完整状态字节在 `_write_lock` 外由旧快照计算，锁只序列化发送，确认读回又在释放锁后；已排队的不同 bit 更新可能使用同一旧值，后写覆盖前写。
- 修复方向：最新状态读取、bit 合并、发送和确认状态的发布应归于同一所有权临界区；保留现有值域与控制门禁。

### R5-007（P2）：重配置取消时可能遗留候选连接

- 位置：`coordinator.py` 行 585～602 附近。
- 因果：旧 client 已关闭，新候选连接正在验证，而异常分支只捕获 `Exception`。Python 的 `CancelledError` 不进入该分支；尚未移交的候选可能继续拥有读任务，coordinator 仍引用已关闭的旧 client。
- 修复方向：明确候选所有权，在取消/失败时关闭未移交连接，并继续传播取消；不能吞掉取消伪装配置成功或创建并行设备会话。

### R5-008（P2）：初始配置忽略已产生的状态预检错误

- 位置：`config_flow.py` 行 170～183 附近。
- 因果：设备信息成功、实时状态读取失败时已设置 `cannot_connect`，但后续仅判断 info 是否存在，仍创建条目，违背当前“两次预检均成功”的配置契约。
- 影响：一次已知失败的预检可能被当作成功保存，而不是停留在可修正表单；瞬态失败之后仍可能恢复，不能称为必然永久不可用。
- 修复方向：存在错误或信息缺失时返回表单；如要接受部分成功，必须先明确改变契约，而非悄悄忽略错误。

### R5-009（P2）：硬件变化触发的重载任务可能在卸载中取消、等待自身

- 位置：`coordinator.py` 行 762～769 将自身 entry 的 reload 任务纳入待卸载 background 集合，行 344～348 的 shutdown 取消并 gather 该集合。
- 因果：本地 HA 2026.7.4 `ConfigEntries.async_reload` 同一协程等待 unload；卸载再次进入 coordinator shutdown，当前 reload task 仍属于被取消/等待集合，可能自取消或自等待，破坏后续 client 关闭和重载。
- 修复方向：采用 HA 独立管理的 reload 调度，不把发起卸载的任务归属于正在卸载的 entry；shutdown 另防御性排除当前任务，不能仅吞 gather 异常。
- 测试缺口：现有 `async_reload` 替身没有进入真实卸载链，因此绿色测试不排除上述路径。
