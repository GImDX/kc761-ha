# 架构决策记录

> 0.1 的 D-003、D-005 等决定保留为已验证 RC 的历史依据。当前 `0.2.0-alpha.3` 扩展范围由 [V0_2_EXPANSION.md](V0_2_EXPANSION.md) 覆盖：允许模拟器中的 `0x52/0x55/0x62/0x63/0x66`、一个结构化谱图实体和控制实体；`0x64` 仍禁止。旧决定没有被改写成已完成实机验收。

日期：2026-08-14

状态说明：Accepted 已接受；Deferred 延后；Rejected 不采用；Proposed 待评审。

## D-001 单仓库、内部分层

状态：Accepted

决定：HACS 集成和协议实现位于同一 Git 仓库；协议实现作为 `custom_components/kc761/protocol/` 内的纯 Python 子包。

理由：

- HACS 要求一个仓库只管理一个集成，运行文件位于集成目录。
- 当前只有一个消费者，拆出 PyPI 包会增加版本、发布和安装失败面。
- 纯协议子包仍可脱离 HA 独立单测，保留未来抽取空间。

后果：首版只有一个 release 版本；协议层禁止引用 HA 类型。

## D-002 首版只支持局域网 TCP

状态：Accepted

决定：设备作为 TCP 服务端，HA 通过用户配置的 host/port 连接。上位机观察到的 7601 作为预填候选，而不是硬编码协议常量。

理由：局域网是手册明确支持的本地接口；BLE 服务 UUID、MTU 和丢包恢复未验证；云与串口不具备足够资料。

## D-003 首版严格只读

状态：Accepted

决定：首版不注册控制实体和写 action；不发送 0x62、0x63、0x64、0x66。

理由：设备允许多通信端同时操作，且写状态、校准和清除具有覆盖、互相干扰或不可恢复风险。当前没有 L 级实机证据。

## D-004 轮询为基线、推送为补充

状态：Accepted

决定：实时状态默认每 5 秒读取，设备信息每 60 秒读取；若设备已经自动上传，则被动解析并更新内存，但集成不修改自动上传状态。

理由：轮询行为可预测，不依赖设备全局设置；5 秒兼顾测量更新和 HA Recorder 负担；被动吞掉推送帧是维持 TCP 流同步的必要条件。

## D-005 完整谱图不进入实体状态

状态：Accepted

决定：不把 1024/2048/4096 道数组作为 sensor state/attributes，不周期写入 Recorder。

理由：数据量和更新频率不适合 HA 状态机，且当前总道数与传输完成条件仍有歧义。

后续：完成实机证据后评审按需返回和独立 Lovelace 卡片。

## D-006 DEVICE_ID 是唯一标识

状态：Accepted

决定：Config Entry 和 Device Registry 使用设备返回的 DEVICE_ID；IP/端口只属于可重新配置的连接信息。

理由：IP 会随 DHCP 或网络迁移变化，不能代表物理设备。重新配置必须验证新地址返回相同 DEVICE_ID。

## D-007 控制能力必须显式启用

状态：Accepted，适用于后续阶段

决定：低风险控制也默认不出现；未来只有用户显式启用、测试环境完成范围/ACK/读回验证后才创建。

校准写入和清除统计不继承普通控制授权，需要单独决策。

## D-008 原始二进制资料保留在本地，Git 固定审阅结论

状态：Accepted

决定：官方 PDF 和五张上位机原始截图保留在开发机并由 `.gitignore` 排除；协议证据文档记录文件名、大小、SHA-256 和审阅结论。仓库另含便于代码审阅的 Markdown 转录和两张封面派生图，但它们不替代原始文件、也不提高证据等级。

理由：实现结论必须能追溯到确切资料版本，但厂商资料的公开再分发授权尚未确认。仅记录哈希既能固定证据身份，也避免把二进制资料永久写入未来 HACS 公共仓库历史。

后果：新开发机需要从获授权渠道单独取得原始资料；公开 README 不依赖这些文件才能理解或安装集成。稳定发布前仍需单独复核转录内容及派生图的再分发授权；软件 MIT 许可不自动覆盖厂商资料。

## D-009 不自动发现局域网设备

状态：Accepted for v1

决定：首版只提供手工 Config Flow，不声明 DHCP、mDNS、SSDP 自动发现。

理由：手册没有发现协议、服务广播或稳定主机名证据。使用未验证的端口扫描会增加网络噪声和误识别。

## D-010 BLE 延后

状态：Deferred

启用 BLE 前必须确认：

- 服务 UUID；
- HA 主机蓝牙能力和代理支持范围；
- MTU 至少 185、优选 507 的协商行为；
- 通知分片、丢包、重复和补读；
- BLE 自动上传对其它连接的影响；
- Config Entry 如何在 TCP/BLE 间保持同一 DEVICE_ID。

设备是否在线、是否处于可发现状态尚未确认；任何阴性 BLE 扫描结果均不具备证明力，不能据此推断服务 UUID。

## D-011 串口与云不实现

状态：Rejected for current scope

决定：不根据上位机按钮猜测串口参数；不实现明文科创云协议或自建云兼容逻辑。

重新评审需要新的官方协议或真实设备证据，以及明确的用户需求。

## D-012 累计量作为可重置普通实体

状态：Accepted

决定：RAD0/RAD1/RAD2 的四个 A5 累计字段在通道已安装时创建普通 sensor。`MC_RUNTIME` 和 `SUM_DOSE_TIME` 使用秒 duration；`SUM_DOSE` 和 `SUM_DOSE_EQ` 按正文及当前 rate 统一显示为 `mGy`/`mSv`。所有累计实体不设置 state class，也不使用 `TOTAL_INCREASING`。

理由：设备可由 `0x66` 清空并频繁重置累计值，不能将其承诺为单调累计量；手册表格的 `uGy/uSv` 与正文的 `mGy/mSv` 矛盾仍保留为协议风险，不以实现单位掩盖该事实。

## D-013 Git 与发布边界

状态：Accepted

决定：本地仓库初始分支为 `main`。初始文档回合不创建远端、不推送、不发布 HACS 版本。

后续提交到 GitHub 前，必须核对授权、仓库元数据、提交者 noreply 身份、CI 和源资料公开许可。

后续经用户逐项授权，已创建公开仓库、推送 `main` 与验证分支并建立 Draft PR；这些动作不等于创建 Release。`ci/kc761-v0.1.0-rc1-validation` 在文档基线之上实现只读模拟候选，不代表真实设备已验证；本次审查修复仍未合并 `main`、未创建 tag 或 Release。

## D-014 A1 只发布完整且有界的自动上传轮次

状态：Accepted

决定：A3 自动上传状态帧作为 A1 谱图轮次边界；assembler 只维护固定 2048 道、单一 source 的内存缓冲，支持乱序和精确重复，只有完整轮次才更新最新 `SpectrumSnapshot`。缺片、冲突、越界、断线或新一轮到达时丢弃未完成数据；未知标志和 A4 不解释，不改变设备自动上传设置。

理由：自动上传没有独立请求 SYNC，且手册允许丢包和格式变化；有界、按轮次隔离的策略可避免跨通道/跨轮次污染，也不会把部分数组写入 HA 状态或 Recorder。真实设备的自动上传开启态和跨型号总道数仍需单独 L 级证据。
