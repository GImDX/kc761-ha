# 架构决策记录

> 0.1 的严格只读决定保留为历史依据。当前 `0.2.0-rc.1` 允许读取 `0x52/0x53/0x54/0x55`，并实现默认关闭的 `0x62/0x63/0x66`；`0x64` 始终禁止。写命令的软件实现和模拟器验收不等于实机写入证据。

更新：2026-08-27

状态说明：Accepted 已接受；Deferred 延后；Rejected 不采用；Proposed 待评审。

## D-001 单仓库、内部分层

状态：Accepted

决定：HACS 集成和协议实现位于同一 Git 仓库；协议实现作为 `custom_components/kc761/protocol/` 内的纯 Python 子包。

理由：

- HACS 要求一个仓库只管理一个集成，运行文件位于集成目录。
- 当前只有一个消费者，拆出 PyPI 包会增加版本、发布和安装失败面。
- 纯协议子包仍可脱离 HA 独立单测，保留未来抽取空间。

后果：首版只有一个 release 版本；协议层禁止引用 HA 类型。

## D-002 当前支持 TCP 与显式 BLE 端点

状态：Accepted

决定：TCP 由用户配置 host/port；BLE 从 HA Bluetooth manager 的可连接广播中选择地址，也允许手动地址和已验证服务 UUID 覆盖。两种传输都必须在预检中返回同一类设备信息和状态。

理由：局域网是手册明确支持的本地接口；一台授权设备已确认 BLE 服务、RX/TX 和只读通知。单台证据不足以声明跨固件发现 matcher，因此不做无标识自动连接。云与串口仍不具备足够资料。

## D-003 v0.1 严格只读基线

状态：Accepted as historical baseline；由 D-007 扩展

决定：v0.1 不注册控制实体和写 action；不发送 0x62、0x63、0x64、0x66。v0.2 RC 只能按 D-007 的显式门禁开放前三个已实现写命令；`0x64` 不变。

理由：设备允许多通信端同时操作，且写状态、校准和清除具有覆盖、互相干扰或不可恢复风险。当前没有 L 级实机证据。

## D-004 轮询为基线、推送为补充

状态：Accepted

决定：实时状态默认每 5 秒读取，设备信息每 60 秒读取；自动上传帧被动解析。修改自动上传状态属于 `0x62` 控制，只在设备控制门禁开启时可用。

理由：轮询行为可预测，不依赖设备全局设置；5 秒兼顾测量更新和 HA Recorder 负担；被动吞掉推送帧是维持 TCP 流同步的必要条件。

## D-005 完整谱图点阵不进入 Recorder

状态：Accepted

决定：结构化谱图实体的 state 是总计数；2048 点数组可作为当前属性供本地卡片消费，但必须使用 `_unrecorded_attributes` 排除 Recorder，并避免无变化时重复序列化。历史数据使用独立有界 gzip 存档。

理由：卡片需要当前完整谱图，但点阵不适合长期写入 Recorder。当前实机已确认一个 2048 道组合；其它型号仍需兼容性证据。

后果：WebSocket/卡片和存档复用同一 `SpectrumSnapshot`；每个配置条目最多保留 256 份。

## D-006 DEVICE_ID 是唯一标识

状态：Accepted

决定：Config Entry 和 Device Registry 使用设备返回的 DEVICE_ID；IP/端口只属于可重新配置的连接信息。

理由：IP 会随 DHCP 或网络迁移变化，不能代表物理设备。重新配置必须验证新地址返回相同 DEVICE_ID。

## D-007 控制能力必须显式启用

状态：Accepted and implemented

决定：`enable_device_controls` 默认关闭，关闭时不创建 write switch/select/校时按钮，Coordinator 也拒绝 `0x62/0x63`。`enable_destructive_actions` 是第二层门禁，且只有前者开启时才允许 `0x66` 和清空 UI。

校准写入 `0x64` 永久不进入当前命令集合。清空统计只接受逐通道、逐类别白名单 mask；前端显示不构成授权，后端始终复查门禁。

## D-008 原始二进制资料保留在本地，Git 固定审阅结论

状态：Accepted

决定：官方 PDF 和五张上位机原始截图保留在开发机并由 `.gitignore` 排除；协议证据文档记录文件名、大小、SHA-256 和审阅结论。仓库另含便于代码审阅的 Markdown 转录和两张封面派生图，但它们不替代原始文件、也不提高证据等级。

理由：实现结论必须能追溯到确切资料版本，但厂商资料的公开再分发授权尚未确认。仅记录哈希既能固定证据身份，也避免把二进制资料永久写入未来 HACS 公共仓库历史。

后果：新开发机需要从获授权渠道单独取得原始资料；公开 README 不依赖这些文件才能理解或安装集成。稳定发布前仍需单独复核转录内容及派生图的再分发授权；软件 MIT 许可不自动覆盖厂商资料。

## D-009 不自动发现局域网设备

状态：Accepted for v1

决定：首版只提供手工 Config Flow，不声明 DHCP、mDNS、SSDP 自动发现。

理由：手册没有发现协议、服务广播或稳定主机名证据。使用未验证的端口扫描会增加网络噪声和误识别。

## D-010 BLE 广播地址选择，GATT 自动连接仍延后

状态：Accepted for address selection; unsupported-device discovery Deferred

决定：Config Flow 的 BLE 步骤使用 HA Bluetooth manager 的 connectable 广播缓存和短时 active scan 展示地址选择器，同时保留 `custom_value` 手动输入回退。选择阶段只读取广播，不建立 GATT 连接。提交后通过 HA Bluetooth manager 解析 `BLEDevice`，枚举 GATT 服务并唯一匹配手册给出的 RX/TX 特征。对当前已验证设备默认约束服务 UUID `59462f12-9543-9999-12c8-58b459a2712d`；兼容固件必须由用户显式输入另一个已验证 UUID 覆盖。集成不声明跨型号 Bluetooth matcher，不执行无标识 GATT 自动连接，也不启动独立扫描器。

自动识别设备身份和稳定发布前仍必须确认：

- 跨固件服务 UUID 一致性；
- HA 主机蓝牙能力和代理支持范围；
- MTU 至少 185、优选 507 的协商行为；本次 BlueZ `mtu_size=23` 仅作为 placeholder，不能当作协商值；
- 通知分片、丢包、重复和补读；
- BLE 自动上传对其它连接的影响；
- Config Entry 如何在 TCP/BLE 间保持同一 DEVICE_ID。

单台设备已取得服务、特征、通知和只读协议证据，但设备是否跨固件保持同一服务或处于可发现状态仍未确认；任何阴性 BLE 扫描结果均不具备证明力。当前 BLE 证据不提升 `hardware_verified`。

## D-011 串口与云不实现

状态：Rejected for current scope

决定：不根据上位机按钮猜测串口参数；不实现明文科创云协议或自建云兼容逻辑。

重新评审需要新的官方协议或真实设备证据，以及明确的用户需求。

## D-012 累计量作为可重置普通实体

状态：Accepted（2026-09-06 原始单位裁定更新）

决定：RAD0/RAD1/RAD2 的四个 A5 累计字段在通道已安装时创建普通 sensor。`MC_RUNTIME` 和 `SUM_DOSE_TIME` 使用秒 duration；2026-09-06 用户明确确认原始累计数值单位为 `mGy/mSv`，因此 `SUM_DOSE` 和 `SUM_DOSE_EQ` 保留当前 `mGy`、`mSv` 标签和数值。所有累计实体不设置 state class，也不使用 `TOTAL_INCREASING`。A2 速率字段继续使用线协议原生 `mGy/h`、`mSv/h`。

理由：设备可由 `0x66` 清空并频繁重置累计值，不能将其承诺为单调累计量。PDF 的 DEVICE_INFO 表逐字段写 `uGy/uSv`，官方上位机截图显示 `µGy/µSv`，下一页正文写成顺序颠倒的“mSv/mGy”；这些原始材料仍原样保留。此前根据表格/UI 推导“只修正为微单位标签”的方案被本次用户确认取代。此次为用户确认的项目单位裁定，不伪装成本轮新取得的协议抓包或跨固件物理测量证据。2026-08-27 Recorder 速率复核仍仅证明 A2 的量级，不能独立验证 A5。

实现状态：当前 RC 原始累计实体的 `mGy/mSv` 标签符合本次裁定，不改写既有 Recorder 历史。用户另行接受可选微单位显示：`mGy→µGy`、`mSv→µSv` 及对应速率必须同时将数值乘 1000；Gy 与 Sv 不互换。实现前应验证目标 HA 的 Recorder/长期统计对同实体单位切换的兼容性；不兼容时保留原始实体并提供独立微单位实体，避免混用统计序列。内部协议、缓存与原始诊断始终保留原始数值。实施与验收记录见 [PRE_RELEASE_COVERAGE.md](PRE_RELEASE_COVERAGE.md)。

## D-013 Git 与发布边界

状态：Accepted

决定：本地仓库初始分支为 `main`。初始文档回合不创建远端、不推送、不发布 HACS 版本。

后续提交到 GitHub 前，必须核对授权、仓库元数据、提交者 noreply 身份、CI 和源资料公开许可。

后续经用户逐项授权，已创建公开仓库并保留 v0.1 验证分支/历史 PR。`0.2.0-rc.1` 必须在独立发布工作树完成原子提交、推送发布分支和 CI；只有 CI 全绿后才允许快进 `main` 并创建指向同一提交的 prerelease。历史分支不得被删除或改写以伪造当前验收。

## D-014 A1 只发布完整且有界的自动上传轮次

状态：Accepted

决定：A3 自动上传状态帧作为 A1 谱图轮次边界；assembler 只维护固定 2048 道、单一 source 的内存缓冲，支持乱序和精确重复，只有完整轮次才更新最新 `SpectrumSnapshot`。缺片、冲突、越界、断线或新一轮到达时丢弃未完成数据；未知标志和 A4 不解释，不改变设备自动上传设置。

理由：自动上传没有独立请求 SYNC，且手册允许丢包和格式变化；有界、按轮次隔离的策略可避免跨通道/跨轮次污染，也不会把部分数组写入 HA 状态或 Recorder。真实设备的自动上传开启态和跨型号总道数仍需单独 L 级证据。
